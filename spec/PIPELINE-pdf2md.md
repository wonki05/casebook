# 제안 — 표준판례 PDF → Markdown(하위 모델) → 병합·빌드(상위 모델) 분업 구조

> 상태: **제안(미구현)**. 2026-10-24. 현재 저장소의 규칙(공식 텍스트는 law.go.kr 에서만, 등록은 add_cases.py 로만, 템플릿 불변)을 그대로 지키면서
> 표준판례 PDF 5건(헌법 323p · 행정법 442p · 민법 659p · 형법 454p · 상법 548p, 상법만 515개 항목)을 사람 손을 거의 거치지 않고 등록부에 옮기기 위한 구조다.

## 0. 출발점 — PDF 안에서 무엇이 "데이터"인가
표준판례 PDF 의 한 항목은 대체로 `번호. 제목 / (법원 선고일 선고 사건번호 판결) / <주제> / <쟁점> / <판결요지> / <선정이유>` 로 되어 있고, 앞머리 **목차가 전 항목의 번호·제목·인용·쪽수를 다시 한 번 적어 준다**(상법 목차 40쪽, 515개 항목).
저장소 규칙상 화면에 싣는 판시사항·요지·전문은 PDF 가 아니라 law.go.kr 에서 받으므로, PDF 에서 꼭 가져와야 하는 것은 아래뿐이다.

| 필드 | 출처 | 누가 만들 수 있나 |
|---|---|---|
| 사건번호·선고일·법원·전원합의체 여부 | 목차 + 본문 인용 괄호 | **스크립트**(정규식; `tools/casenum.py` 이미 있음) |
| tocPath(분야›편›장[›절]) | 목차 + 본문 면주(페이지 머리글) | **스크립트**가 1차, 애매한 것만 모델 |
| title(학습용 짧은 제목) | 목차의 항목 제목(대부분 10~20자) | 스크립트 그대로 쓰고, 20자 초과만 하위 모델이 줄임 |
| selectionReason(선정이유) · keywords(주제) · 쟁점 | 본문 | **하위 모델**(본문을 Markdown 으로 옮기면서 필드 분리) |
| editorial(대체 요지) | 본문 <판결요지> | 하위 모델이 옮긴 것을 그대로(법령정보센터에 미게재인 옛 판례 대비 대체물) |
| 교차검증 자료 | 본문 <판결요지> vs. fetched 요지 | **스크립트**(유사도) → 불일치만 상위 모델 |

따라서 "PDF 전체를 모델이 옮긴다"가 아니라 **목차 뼈대는 스크립트, 본문 필드는 하위 모델, 판정·병합은 상위 모델**로 나눈다. 하위 모델 단계 없이도 뼈대만으로 등록·수집·빌드까지 갈 수 있고, 하위 모델 산출물은 거기에 살을 붙인다.

## 1. 폴더 구조 (과목별, `data/standard-cases/<과목>/`)
```
data/standard-cases/
  표준판례(2023년 개정판)_상법.pdf
  상법/
    skeleton.json        # [스크립트] 목차에서 뽑은 전 항목 뼈대: no·title·citation·caseNumber·date·court·enBanc·tocPath·bodyPage
    00_toc.md            # [스크립트] 목차 트리(분야›편›장›절)와 toc.json id 대응표 — 사람이 한 번 훑어 확정
    chunks/
      c001_p045-p070.txt # [스크립트] 장(章) 경계에서 자른 본문 텍스트 15~20쪽 단위, 머리에 "현재 위치: 총칙·상행위 › 제1편 총칙 › 제2장 상인" 과 "기대 항목: 2~13" 명시
    md/
      c001.md            # [하위 모델] 청크 1개 → Markdown 1개 (항목마다 H2 블록, 아래 §2 형식)
      _report.json       # [스크립트] md_validate 결과: 항목별 ok / warn / error 와 사유
    entries.jsonl        # [스크립트] md 를 파싱해 1항목 1행으로 편 것 (skeleton 과 번호로 결합)
    candidates-commercial.json   # [스크립트+상위 모델] 기존 후보 파일 형식(status ok) → add_cases.py add --from
    _crosscheck.json     # [스크립트] fetched 요지 vs PDF 요지 유사도, 불일치 목록
```
Markdown 을 중간 형식으로 두는 이유: 하위 모델이 JSON 보다 훨씬 안정적으로 쓰고, 사람이 diff 로 검수할 수 있고, 과목 폴더에 그대로 남아 PDF 를 다시 열지 않아도 되는 보관본이 된다. 파싱은 스크립트가 한다.

## 2. 하위 모델의 산출 형식 (항목 1개 = H2 블록 1개, 기계가 파싱)
```markdown
## 4. 의사나 의료기관의 상인 여부
- 출처: 대법원 2022. 5. 26. 선고 2022다200249 판결          ← PDF 표기 그대로
- 사건: 2022다200249 | 2022-05-26 | 대법원 | 전원합의체 아니오   ← 정규화. 사건이 둘 이상이면 "- 사건:" 줄 반복(첫 줄이 대표)
- 위치: 총칙·상행위 > 제1편 총칙 > 제2장 상인 > (절 없음)
- 쪽: 5

### 주제
(PDF 그대로)
### 쟁점
(PDF 그대로)
### 판결요지
(PDF 그대로 — 화면에는 쓰지 않고 대체 요지·교차검증용)
### 선정이유
(PDF 그대로)
```
하위 모델 지시문(`tools/prompts/pdf2md.md`, 한 파일로 고정)의 핵심 규칙: 요약·의역·교정 금지(줄바꿈으로 끊긴 단어만 붙임) · 없는 절은 `### 주제` 아래 `(없음)` · 읽을 수 없으면 `[판독불가 p.N]` · 번호와 제목은 청크 머리의 "기대 항목" 범위를 벗어나지 않음 · 항목을 만들어 내지 않음 · 한 청크에 걸친 항목은 뒤 청크가 `(이어짐)` 으로 시작.
모델별 차이는 없다(Claude Sonnet, GPT-6 Terra 등 어느 것이든 같은 지시문·같은 청크·같은 출력 경로). 실행 방식은 세 가지 중 택일: ① Claude Code 안에서 `Agent`(model: sonnet) 를 청크 수만큼 병렬 실행(각 에이전트는 자기 md 파일 하나만 씀) ② Anthropic Message Batches / OpenAI Batch 로 야간 일괄 처리(절반 비용) ③ 수동(채팅창에 청크 붙여 넣고 결과 저장).

## 3. 단계와 담당
| 단계 | 도구(신규) | 담당 | 입력 → 출력 | 실패 시 |
|---|---|---|---|---|
| 0 뼈대·청크 | `tools/pdf_chunks.py <pdf>` | 스크립트 | PDF → skeleton.json · 00_toc.md · chunks/*.txt | 목차 파싱 건수 ≠ 본문 항목 수면 중단하고 보고 |
| 1 전사 | `tools/prompts/pdf2md.md` | **하위 모델** ×N(병렬) | chunks/cNNN.txt → md/cNNN.md | 누락 청크만 재실행(`--only c007`) |
| 2 검증·파싱 | `tools/md_validate.py <과목>` | 스크립트 | md/*.md → entries.jsonl · _report.json | error 가 있는 항목만 3단계로 |
| 3 판정·병합 | `tools/md_merge.py <과목>` + 상위 모델 | **상위 모델**(error/warn 만) | skeleton + entries + toc.json → candidates-<subject>.json | 모델이 해당 쪽 chunk 텍스트를 다시 읽고 고침(PDF 재열람 불필요) |
| 4 등록·수집·빌드 | 기존 `add_cases.py add --from` → `fetch_lawgo.py --all-missing` → `make data build check` | 스크립트(사용자 PC) | registry · fetched · dist | .missing 목록 보고(기존 절차) |
| 5 교차검증 | `tools/crosscheck.py <과목>` | 스크립트 → 상위 모델 | fetched 요지 vs PDF 요지 유사도 → _crosscheck.json | 유사도 낮은 건 = 사건번호 오인·병합사건·다른 판결 가능 → 상위 모델이 판정 |

2단계 검증 항목(모두 결정적): 번호 연속성과 skeleton 일치 · 사건번호 정규식(`casenum.CASE_RE`)·선고일 ISO 변환 가능 · 법원과 사건부호 일치(헌 → 헌법재판소) · 위치 문자열이 toc.json 경로로 해석됨(라벨 퍼지 매칭) · 청크 간 중복 번호 없음 · 필수 절(판결요지) 존재 · `[판독불가]` 개수.
상위 모델이 보는 것은 `_report.json` 의 error/warn 항목, 목차 매핑이 모호한 항목, 20자 넘는 제목 축약 검수, 그리고 5단계 불일치뿐이다. 전체 515건을 다시 읽지 않는다.

## 4. 설계상 미리 정할 것 (상위 모델이 3단계에서 따르는 규칙)
- **같은 사건이 여러 항목에 실릴 때**(예: 상법 97다48319 가 수표 편에 3회): 등록은 1회(첫 등장 tocPath), 나머지 위치는 `memo` 에 "함께 실린 곳: 어음·수표 › 제3편 수표 (364·368)" 로 남긴다. 나중에 `tocPaths`(복수) 필드를 스키마에 더할지는 별도 결정.
- **한 항목에 사건이 둘 이상**(형법에 흔함: "헌법재판소 91헌가4; 대법원 2013도1685"): 첫 사건을 등록하고 나머지는 같은 title 에 "(2)" 를 붙여 각각 등록. 모두 같은 tocPath·selectionReason.
- **절(Ⅰ. Ⅱ. …) 층**: toc.json 깊이 3 을 넘는 과목(상법: 분야›편›장›절)은 절을 목차에 넣지 않고 `keywords` 첫 항목으로 둔다. 편›장›절 3단계인 과목(헌법·민법·행정법)은 toc.json 을 PDF 목차로 교체한 뒤 절까지 tocPath 로 쓴다(기존 시안 사건은 `set --toc` 로 이동).
- **editorial 채움 여부**: PDF <판결요지>·<쟁점>을 `editorial.holding`·`editorial.issues` 에 넣되 `editorialSource: "표준판례(2023) p.N"` 을 함께 기록한다. 공식 텍스트가 수집되면 자동으로 묻히고(현재 build_data 동작), 미게재 사건만 "편집 요약" 표시로 보인다.
- **선고일 표기 불규칙**("2001.02.13.", "2008.11. 27.")과 "판결" 누락("2013다50165"): 정규화는 스크립트가 하고 원문은 `출처:` 줄에 남긴다.

## 5. 규모·비용 가늠
- 청크 크기 15~20쪽(≈ 25~35k 자) → 과목당 25~45개, 5과목 합계 약 140개. 청크당 하위 모델 입력 ≈ 25k 토큰, 출력 ≈ 15k 토큰.
- 상위 모델은 error/warn(경험상 5~15%)과 교차검증 불일치만 본다 → 과목당 수십 건.
- 수집(law.go.kr)은 사건 수에 비례(상법 ≈ 500건, 1.5초 간격이면 15분 안팎). 옛 판례(1960~80년대)는 미게재가 있을 수 있어 editorial 대체물이 의미가 있다.

## 6. 구현 순서(실행 결정 후)
1. `pdf_chunks.py`: 상법으로 먼저(목차가 가장 정형). skeleton.json 과 00_toc.md 가 toc.json(`sb-*`)과 1:1 로 맞는지 확인 — 이 단계만으로 `candidates-commercial.json`(selectionReason 없는 상태)을 만들어 등록·수집·빌드가 되는지 본다.
2. `tools/prompts/pdf2md.md` + `md_validate.py`: 청크 2~3개로 하위 모델 시험 → 형식 위반 유형을 보고 지시문 보강.
3. `md_merge.py` · `crosscheck.py` → 상법 전체 → 보고서. 그다음 헌법(절 3단계) → 나머지.
4. CLAUDE.md 레시피 A 를 이 절차로 바꾸고, Makefile/make.py 에 `std-skeleton` `std-validate` `std-merge` 타깃 추가.

- 권장 조합: 1단계 sonnet-low 배치(≈7M 토큰, ≈$18) + 3·5단계 fable medium(≈3.7M 토큰) ≈ 총 11M 토큰. 0단계(뼈대)·4단계(수집)는 모델 토큰 0.
